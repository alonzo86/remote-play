# Network protocol, version 5

This document uses ASD-STE100 style. Code: `scripts/core/protocol.gd`.

## Ports

| Port | Type | Use |
|------|------|-----|
| 47801 | TCP | WebSocket server on the TV. Path and query are not used. |

The TV sends nothing on the network by itself. A phone finds the TV in one of two ways: the player types the room code that the TV shows, or the phone scans the QR code of the TV (`ws://IP:47801/ROOM`). There is no list of TVs and no search.

## Room code

The room code is the address of the TV in 4 letters (FD-28). It holds the last two numbers of the IPv4 address of the TV (for `192.168.1.23`: `1` and `23`), which are 16 bits: `v = third * 256 + fourth`.

- **Scramble.** Before the letters are made, the 16 bits go through a fixed one-to-one step, so that the codes on one network do not all look alike: `n = (v * 40503) mod 65536`. The phone undoes it with `v = (n * 30599) mod 65536` (`40503 * 30599` is 1 modulo 65536).
- **Letters.** `n` is written as 4 digits of base 22 with the alphabet `ACDEFGHJKLMNPQRTUVWXYZ`, first digit first. The alphabet has no digit and leaves out B, I, O and S, which look like 8, 1, 0 and 5 (a child reads the code from the TV and types it, issue #241); `tests/room_code.gd` checks it. A change of the alphabet changes every room code, so it needs a new `VERSION` (the `change-protocol` skill); the 22 letters are kept in this order. `192.168.1.23` gives `DREJ`. The first letter uses only the first 7 letters of the alphabet, because `n` is below 65536.
- **Reading.** The phone removes spaces and changes to upper case. A text with another length, a letter that is not in the alphabet, or a value above 65535 is not a room code: the phone shows the error at once and sends nothing.
- **Address.** The phone takes the first two numbers from its own Wi-Fi address (the private IPv4 addresses of the best kind, see `Protocol.private_ipv4s`) and the last two from the code, and connects to port 47801. With several addresses it tries each one, one after the other, with one try and a timeout of 2 s for each (`ControllerClient.connect_to(..., quick)`). If none answers, the phone says that the room is not found and suggests the QR code. A network where the TV and the phone do not share the first two numbers needs the QR code.
- **TV.** The TV uses its LAN address (`Protocol.local_ipv4`: `192.168.x.x`, else `10.x.x.x`, else `172.16.x.x` to `172.31.x.x`), reads it again each second, and shows a new code when it changes. A TV with no address has no code and no QR code.
- **Check.** The TV answers `bad_room` to a `hello` whose `room` is not its own code, so a typed code that reaches another device with the right port, or another TV, does no harm. A `room` that is empty is accepted only by a debug build of the TV (`OS.is_debug_build()`; a run on a desktop: `--join=127.0.0.1`); a release build answers `bad_room` (issue #388).

The room code is not a password: it is the address. Any device on the network can build it, and the TV asks for nothing else, except the approval of the host when the setting "approve new players" is ON (FD-30, "Approval" below; there is no join PIN since FD-28). The traffic is not encrypted.

## Join (WebSocket, JSON text frames)

| From | Message | Meaning |
|------|---------|---------|
| Phone | `{"t":"hello","v":5,"room":"DREJ","token":"","name":"","pid":"","av":-1}` | First message. `room` can be empty only in a development run (a debug build of the TV accepts it, a release build answers `bad_room`). `token` is empty for a new player. `name` can be empty: the TV then shows "Player N". `pid` and `av` are optional: the profile ID (32 lower-case hex characters) and the avatar index (0 to 255) of the profile that plays (FD-22, "Profiles" below). |
| TV | `{"t":"welcome","slot":0,"token":"…","color":"#3dcef2","phase":"connect","name":"Living Room TV","lang":"en","pid":"","av":-1,"pname":""}` | Accepted. Optional `rc`: `false` when the running game has no Recenter box on the pad (REQ-GM-37; absent means true). Optional `ab`: the buttons of the running game, as in `phase` (REQ-GM-37a; absent means `"ab"`). The phone saves `token`. `pid`, `av` and `pname` are the profile that the TV accepted (empty or -1 for a guest). `name` here is the name of the TV; the player name is `pname`, the name that the TV shows (with a number when another player has the same name, for example `Sam 2`). `lang` is the language of the TV, `en` or `he`; the field is optional (a TV of an older build does not send it) and the phone keeps its own language then (REQ-FL-62). |
| TV | `{"t":"reject","reason":"full"}` | `reason`: `full`, `bad_room`, `version`. |
| TV | `{"t":"pending"}` | The TV has the `hello` and waits for its host to allow the phone (FD-30, "Approval"). Sent when the request is queued and again every 2 seconds (`PENDING_KEEPALIVE_MS`) until the wait ends. The phone shows its waiting screen and sends nothing more (only `bye` to cancel). It has no field and carries no time. Sent only by a TV whose setting is ON. A phone of an older build ignores it, but the frame keeps its 5 second `hello` clock from closing the socket. |
| TV | `{"t":"kicked","reason":"refused"}` | The phone gets no slot. `refused`: the host refused it, or its address is blocked (3 host refusals in a row, 60 s), or the setting went OFF while it waited. |
| TV | `{"t":"kicked","reason":"timeout"}` | The phone gets no slot. The host did not answer: 60 s with the request shown, or 180 s in total. |
| TV | `{"t":"kicked","reason":"busy"}` | The phone gets no slot. 4 requests already wait. |

The TV closes a connection that sends no `hello` in 5 seconds.

**Approval (FD-30, `docs/JOIN_APPROVAL_PLAN.md`).** `TvServer.approve_new` is false in the code and the App sets it from the setting, so a TV with the setting OFF answers a `hello` exactly as before (the first frame is `welcome`, no `pending`). With it ON, a `hello` is checked in this order: (1) `t` is `hello`; (2) `v` is the version (`reject` / `version`); (3) `room` (`reject` / `bad_room`); (4) a replaced token (`kicked` / `replaced`); (5) a token of a present slot: resume, no card; (6) a **known token** (below): joins again with the same token, no card; (7) a `pid` that a connected phone holds: `kicked` / `replaced`, before any approval; (8) no free slot: `reject` / `full` (a phone that cannot get a slot is never shown); (9) approval OFF: the join of today; (10) else the request waits (`pending`). The request takes no slot and no game sees it. The host allows it (`welcome`, after steps 7 and 8 run again, because the room can change while it waits) or refuses it (`kicked` / `refused`); a request ends as `kicked` / `timeout` after 60 seconds with the card shown (`approval_timeout_ms`) or 180 seconds in total (`approval_total_ms`), shown or not; the card shows only in the menu phases, one at a time, and the next one 1 second after the last (`approval_gap_ms`). A phone that sends `bye` or closes its socket while it waits is removed with no message. When the setting goes OFF, every waiting phone gets `kicked` / `refused`. A **known token** is a token that this TV gave in this run of the TV app and that a `kick`, a `bye` of the phone or a replacement of the slot did not revoke; the TV keeps at most 32 (`MAX_KNOWN_TOKENS`, the oldest goes first) and forgets all of them when the TV app stops. A slot that was freed by the grace time or by "Resume without" keeps its token.

Optional `rc`: `false` while the running game has no Recenter box on the pad (REQ-GM-37, issue #55); absent means true. Optional message: an older phone ignores it, so the protocol `VERSION` stays 2. |
| TV | `{"t":"final","v":"1ST   NOA   12"}` | The line of this player in the result of the game (REQ-FL-67a, issue #455): the text of the row of the player in the result menu of the TV (the place, the name and the score, or "not finished"), at most 60 characters on the phone. Optional message: an older phone ignores it, so the protocol `VERSION` stays 2. |
| TV | `{"t":"turn","s":1,"who":""}` | Whose turn it is in a game with turns (Bowling, REQ-BW-14). `s`: 0 no turn line, 1 the turn of this phone, 2 another player is on turn (`who` is the name of that player, at most 20 characters). `k` is optional: `"golf"` makes the waiting line say that the player is putting (Mini Golf, REQ-MG-12); without it the line says that the player is bowling. Sent once for each change, only while a game runs. The phone shows a line under its score row and clears it at any phase other than `playing` and `paused`, and when it joins again. Optional message: an older phone ignores it, so the protocol `VERSION` stays 3. |
| TV | `{"t":"setup","swing":true,"pick":true,"in":true}` | The settings view of a game is open on the TV (issues #79 and #76). `swing`: the game is a swing game (Bowling, Tennis, Mini Golf): the phone shows the safety card "hold on tight" until the player taps OK, every time the view opens (a phone that tapped for this view answers at once when the TV syncs the view again; REQ-GM-102, issue #148). `pick`: two or more phones are connected: the phone shows the question "play this game?" with IN and OUT (REQ-GM-104). `in`: the choice of this phone as the TV has it. Sent to every connected phone when the view opens and again when a phone joins or leaves, a choice changes or the swing flag changes, so a phone that joins or returns gets it too. Any `phase` message closes it (the phone forgets the setup). |
| Phone | `{"t":"play","v":false}` | The player chose OUT (`false`) or IN (`true`) for the game of the settings view (issue #76, REQ-GM-104). Ignored when no settings view is open. Every phone may go OUT; the next `setup` message carries the choice. A phone that is OUT does not play the next round (it gets the phase `waiting`). |
| Phone | `{"t":"swing_ok"}` | The player tapped OK on the safety card (or had tapped it for this view before the TV synced the view again). The Start button of the TV settings view of a swing game works when every connected phone has sent it. Ignored when no swing setup is open. |
| Phone | `{"t":"leave_ask"}` | The player tapped the pause button of the pad, or pressed Back on the phone, during a game (REQ-FL-52c, issue #435). The TV does what Back on its remote does: it pauses the game and asks "End the game?" with Resume first. The TV ignores it, with no answer and no error, unless the phase is `playing` for this phone (a phone that waits for the next round, and the phases `menu`, `connect` and `paused`, are ignored), the phone is connected, and no question or menu is open (the game decides that); it takes at most one from a phone each `LEAVE_ASK_MIN_MS` (1000 ms, counted from the last one that it took; a request that comes sooner is dropped). It has no field: any other field is ignored. Optional message: an old TV ignores it, so the protocol `VERSION` stays 5. |
| Phone | `{"t":"profile","pid":"…","name":"Noam","av":7}` | The player changed profile on the phone (FD-22). `{"t":"profile"}` alone is a guest. The TV accepts it only in the phases `connect` and `menu`. Optional message. |
| TV | `{"t":"profile","pid":"…","name":"Noam","av":7}` | The answer to every `profile` message: the values the TV accepted (empty for a guest); `name` is the name that the TV shows. In the phases `playing`, `paused` and `waiting` the TV does not change the profile and answers with the stored one. The phone shows the answer as the truth. |
| TV | `{"t":"result","pid":"…","key":"paint_grab|medium","v":340}` | The result of the round for the profile of this phone (FD-22, REQ-GM-99). `key` is the best key of the game, `v` the score as a whole number (a time in milliseconds). Sent at the end of a round to each finished player with a profile and a score above 0; never to a guest or to a lost phone. The phone ignores it when `pid` is not its profile. Optional message: `VERSION` stays 2. |
| Both | `{"t":"bye"}` | Clean leave. The TV frees the slot at once. A phone that waits for the host (`pending`) sends it to cancel: the TV removes the request. The TV also sends it to a waiting phone when the TV app stops. When the TV app closes, it sends `bye` to every phone and closes the sockets 300 ms later (a close right after `bye` can drop it, issue #169); the phone goes to idle and says the TV closed. A TV that is killed sends nothing: the phone sees no frame for `PEER_TIMEOUT_MS` (3 s) and goes to reconnecting. |
| TV | `{"t":"kicked"}` | The host removed this player (Players modal). The slot is free at once and the token is no longer valid. The phone forgets the token, goes to its connect screen, and does not reconnect by itself. Any phone can join the slot again by the normal join. |
| TV | `{"t":"kicked","reason":"replaced"}` | Sent in three cases (see "Profiles"): the same profile joined from another phone while its holder was lost (the holder gets it), or a new phone sent a `hello` with a profile that a connected phone holds (the new phone gets it, and takes no slot), or a request was allowed and the profile of its `hello` is now held by a connected phone. Same effect as `kicked`; the phone shows "THIS PLAYER IS ALREADY IN THE ROOM." (`app.player_already_in_room`) The field `reason` is optional. The reasons `refused`, `timeout` and `busy` (see "Join") are sent to a phone that waits for approval and has no slot; a phone that does not know them treats any other reason as `kicked`. |

Phone computation:

- `rtt = t3 - t0` (`t3` = phone clock when the pong arrives).
- `off = t1 - (t0 + t3) / 2`.

The TV computes the sensor age: `age = tv_receive_time - (packet_ts + off)`.
The error is about +/- RTT/2. Use the trend, not the single value. The value can be below zero.

## Fields of the wrong type

A JSON frame can hold any value in any field (REQ-N10). The TV and the phone read a field only with `Protocol.num` (a finite number), `Protocol.whole` (an integer), `Protocol.text` and `Protocol.flag` (a boolean). A value of another type gives the default of that field, so a `stat` with `"rtt": {}` is taken as `rtt = -1`, a `ping` echoes `id` and `t0` as numbers (0 when they are not), and a `hello` with `"v": [5]` has the wrong version. This is not a change of the protocol: the `VERSION` stays.

## Sensor packet (WebSocket binary frame, phone to TV, about 60 per second)

Little-endian. Size: 36 bytes.

| Offset | Type | Field |
|--------|------|-------|
| 0 | u8 | Type. `1` = sensor |
| 1 | u8 | Flags. Bit 0 = a finger touches the screen |
| 2 | u16 | Sequence number. It wraps. The TV counts gaps as lost packets |
| 4 | u32 | Phone clock in ms (`Time.get_ticks_msec()`) |
| 8 | f32 x3 | Gyroscope x, y, z in rad/s (`Input.get_gyroscope()`) |
| 20 | f32 x3 | Accelerometer x, y, z in m/s2 (`Input.get_accelerometer()`) |
| 32 | u8 | Button bits. Bit 0 = A, bit 1 = B |
| 33 | u8 | Reserved. Send 0 |
| 34 | u8 | Touch x, 0 to 255 over the screen width. While it is the turn of the phone in Bowling (`turn` with `s` 1 and no `k`), the phone sends the place on its aim strip instead, 0 (left end) to 255 (right end), and only for the finger on the strip |
| 35 | u8 | Touch y, 0 to 255 over the screen height |

The phone frame: x = right, y = top of the phone, z = out of the screen.

## Profiles (FD-22)

A profile lives on the phone (`docs/PROFILES_PLAN.md`). The TV keeps it in memory for the session only.

- `pid` is 32 hex characters; the TV makes it lower case. `av` is an integer from 0 to 255; the phone sends 0 to 31 (the sheet has 32 avatars) and the TV shows the slot number for an index it does not know. `name` has at most `NAME_MAX` = 10 characters. The TV keeps only letters of the Latin and Hebrew alphabets, digits and the space (the pixel fonts have no other glyph), and cuts the result at 10.
- A `hello` with no valid `pid` is a guest, also when `name` is not empty (an old phone that sends only a name shows that name and has no avatar). A guest with no name is "Player N".
- The TV makes the shown names different: a name that another player in a lower slot already has (the comparison ignores case and the spaces at the ends) gets " 2", " 3". The names are made again only outside a round, so a name does not change in the middle of a game.
- **The same `pid` on two phones (issue #388, owner decisions of 2026-11-07).** (1) A `hello` with a `pid` that a **connected** phone holds, in any phase and without a token of the room, is answered with `kicked` and `reason` `replaced` (the phone shows "THIS PLAYER IS ALREADY IN THE ROOM."); the TV closes the socket, the phone takes no slot and keeps no token, and the holder is not touched. A `hello` whose token resumes a slot is never sent away for a `pid`; a returning phone with the `pid` of another connected phone is a guest. (2) A `profile` message with a `pid` that another connected phone holds, from a phone that is already in the room (phases `connect` and `menu`), is not refused: the phone stays connected as a guest (the TV ignores its `pid`, `av` and `name`; the `profile` answer says `pid` is empty). Limit: such a guest asks for its profile again only on the next phase message or `welcome` (`controller_client.gd`), so it stays a guest until the TV changes phase. (3) When the holder is **lost** (state LOST, slot kept in grace), a `hello` or a `profile` in `connect` or `menu` wins, also on a full TV (with the approval ON, the takeover for a `hello` happens when the host allows the phone, never when the request is queued): the TV frees the older slot and sends `kicked` with `reason` `replaced` to that phone if it is still connected. The TV remembers the token of the freed slot for 10 minutes (`REPLACED_TOKEN_MS`) and answers a `hello` with that token with the same `kicked`, so a phone that was offline does not come back and replace the newer one. In the phases `playing`, `paused` and `waiting` no slot is freed for a lost holder: the new phone joins as a guest and can send `profile` in the next menu. No message changes, so `VERSION` stays 5.
- A phone that comes back with its token keeps the profile that the TV has for that slot; `pid`, `av` and `name` of that `hello` are ignored outside `connect` and `menu`.

**Copy of a profile.** A profile is copied to another phone with a text that starts with `WP1.`, shown as a QR code only. The phone only reads a code by a scan (IMPORT); there is no paste (removed on 2026-11-02) and no COPY CODE (removed on 2026-11-09), so the clipboard is not used. It never goes over the network of the game and the TV never sees it. The format is in `docs/PROFILES_PLAN.md` section 6.1 (`scripts/core/profile_code.gd`). The QR encoder (`scripts/core/qr_encoder.gd`) goes up to version 14, error correction L, 458 bytes.

All these fields and messages are optional: an old TV or an old phone ignores them. (They were added at `VERSION` 2. `VERSION` 3 added the join PIN, 4 removed it with the beacon and 5 added the safety card of the swing games (`setup` and `swing_ok`, because a TV of version 5 waits for the answer of every phone and an older phone would never give it): a build of another version is rejected with `version`.)

## Slots, loss and reconnect

- The TV has 4 slots. A slot has the state `EMPTY`, `CONNECTED`, or `LOST`.
- When the socket closes or is silent for 3 seconds (`PEER_TIMEOUT_MS`, issue #56), the slot becomes `LOST`. A silent phone is lost at once: the TV does not wait for a close handshake that the phone cannot answer (for example when its Wi-Fi is gone). The TV keeps a lost slot for 5 seconds (`SLOT_GRACE_MS`, issue #44), then frees it. While the game is paused for it (phase `paused`), the TV keeps it for 5 minutes (`PAUSED_SLOT_GRACE_MS`), so that a phone call does not end the game.
- The game pauses while a participant is `LOST`, and it does not go on by itself (REQ-GM-30). The TV user chooses: "Resume without 2P" (the name of the player, or "2P" for a guest) frees the slot of the lost phone (only while another participant is connected), "Resume" goes on when the phones are back, "End game" leaves. A phone that comes back with its token gets its slot again. When the slot is freed (time over, or "Resume without"), a phone that comes back is a new player and waits for the next round. When no participant is left, the game ends with "No players connected".
- The phone reconnects after 0.5 s, 1 s, 2 s, and then every 2 s. It sends the saved `token`.
  The TV gives the same slot back.
- A `hello` with an unknown token is a new player, and needs the approval of the host when the setting is ON. A known token (see "Approval") joins again with no card.
- **Limits of the TV (issue #387, issue #388).** The token is 32 hex characters from `Crypto.generate_random_bytes(16)`. The TV keeps at most 16 connections that have not sent `hello` (`TvServer.MAX_PENDING`; more are closed at once), at most 4 of them from one address (`max_pending_per_ip`, so one device cannot keep the phones of the family out), and accepts at most 30 connections from one address in 10 s (`max_accepts_per_ip`). A socket buffers at most 32768 bytes (`BUFFER_BYTES`) and 1024 frames (about 15 s of sensor packets); a text frame above 4096 bytes (`MAX_TEXT_BYTES`) is dropped without parsing. A sensor packet with a NaN or INF float, or a gyro or accel value above 1000 (`SENSOR_MAX_ABS`, far above what a phone measures), is dropped (`Protocol.decode_sensor`). None of this changes a message, so `VERSION` stays 5. A phone that waits for the host (`pending`) counts as a connection that has not sent `hello`: it counts toward the 16 and the 4. On top of that, at most 4 requests wait at one time (`TvServer.MAX_WAITING`; a fifth `hello` gets `kicked` / `busy`) and an address has at most 1 request (`max_waiting_per_ip`): a new `hello` of that address replaces its request (it keeps the place and the times; the old socket is closed with no message; when the old request was already shown on the card, the new one gets a new id and shows again after the 1 s gap, so a late allow of the old id does nothing). Every per-address table (the accept window, the pending count, the waiting list and the refusals) uses one key (`TvServer.address_key`): an IPv4-mapped IPv6 address (`::ffff:1.2.3.4`) is the IPv4 address, an IPv6 address is its /64 prefix, an IPv4 address stays as it is. Phones behind one address (a NAT, a hotspot, 127.0.0.1 in tests) share one waiting request, the waiting cap and the refusal block: an accepted limit. After 3 host refusals in a row from one address (`refuse_block_after`) the address is blocked for 60 seconds (`refuse_block_ms`) and its count goes back to 0: a `hello` in the block gets `kicked` / `refused` at once and does not count. An allow sets the count to 0; a timeout, a cancel, a replacement and the setting OFF do not change it. The TV keeps this table in memory for the run of the TV app, for at most 64 addresses (`max_refusal_entries`; when it is full the oldest count that is not blocked is forgotten). A waiting socket is read for at most 8 frames in each frame (`MAX_WAITING_FRAMES`).
- **The `pid` is not a secret (issue #388).** Profile sharing hands the `pid` to other phones on purpose, so a second phone can know it. The TV protects the profile of a connected phone: a newer phone that joins with the same `pid` is sent away with `kicked` / `replaced`, and a phone that is already in the room becomes a guest (above, REQ-FL-74). A holder that is lost can still be replaced, because that is how a family moves a profile to a new phone. Binding the `pid` to the token is not done. The effect is limited to the menu phases, and the host can remove any player.
- The phone gives up and shows an error only when the first connection fails 3 times, or when the TV sends `reject`. A phone that waits for the host (state `WAITING` after `pending`) never sends `hello` again and never retries: when the TV closes the socket or sends no frame for 5 seconds (`HELLO_TIMEOUT_MS`), it goes to idle with the reason `wait_lost`; `kicked` with `refused`, `timeout` or `busy` ends the wait the same way, and a `bye` of the TV is `tv_closed`.
- The phone also gives up (and returns to the connect screen) when the user taps "Disconnect".

## Version change

Change `VERSION` in `protocol.gd` when an old peer would misread the packet layout or a message, or when the new message is one that the other side **waits for**. A new optional field or message that nobody waits for does not change it (`lang`, `score`, `turn`, `profile`). A new message that one side waits for is incompatible, because an old peer never sends it: `setup` and `swing_ok` raised `VERSION` to 5 for that reason (a TV of version 5 waits for the answer of every phone). The TV rejects other versions. `pending` and the reasons `refused`, `timeout` and `busy` of `kicked` keep `VERSION` at 5: nobody waits for `pending` (a phone of an older build ignores it and waits for `welcome` as before, and the frame keeps its 5 second `hello` clock from closing the socket, FD-30.7), `kicked` already exists, and an older phone shows the text of `kicked` for the new reasons (FD-30.11).

`lang` and `welcome.lang` are still sent but the phone ignores them (issue #171). Remove both at the next `VERSION` bump (`LANG_REMOVE_AFTER_VERSION` in `protocol.gd`; `tests/protocol_doc.gd` fails if the bump is made and `lang` is still there).

**What keeps this document true.** `Protocol.MESSAGES` lists every message and its sender. `tests/protocol_doc.gd` checks that the messages of the tables above, the `"t"` values written in `scripts/net/tv_server.gd` and `scripts/net/controller_client.gd`, and `Protocol.MESSAGES` are the same set with the same senders, and that the version, the port, the size of the sensor packet, the time-outs, the number of slots and `NAME_MAX` quoted in this document are the values in `protocol.gd`.
