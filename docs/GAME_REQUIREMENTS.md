# Game requirements

These requirements apply to every minigame. Each game also has its own list in `docs/games/<id>.md`.
The system requirements (network, phone, TV, export) are in `docs/REQUIREMENTS.md`.

Style: ASD-STE100 Simplified Technical English. "Must" is mandatory. "Should" is a goal that a game may skip
if its own requirements file says why.

## How the requirements work

- REQ-GM-1: Each game has a requirements file `docs/games/<id>.md`. `<id>` is the id in `scripts/game/registry.gd`.
- REQ-GM-2: The game requirements file lists the general requirements it does not meet yet (gap) or does not need (exception), and why. All others apply.
- REQ-GM-3: Each requirement has an ID and a status. Statuses: **Done** (built), **Open** (not built), **Device** (only a test on real hardware can check it).
- REQ-GM-4: Code comments and tests use the requirement ID, for example `# REQ-MR-7`.
- REQ-GM-5: A change to the behavior of a game must change its requirements file in the same commit.
- REQ-GM-6: The registry entry of a game has a `doc` field with the path of its requirements file. A test checks that the file exists.
- REQ-GM-6a: Ids and names (issue #231). The internal id of a game (registry `id`, the file `docs/games/<id>.md`, the folder in `scripts/game/` and `assets/tiles/`) can differ from the name that the user sees, because a game was renamed after the id was made. The id never changes; the name is the English text of the `title` key. ## All games (2D and 3D)

Architecture

- REQ-GM-10: A game extends `scripts/game/minigame.gd` (2D) or `scripts/game/minigame_3d.gd` (3D) and is listed in `scripts/game/registry.gd`.
- REQ-GM-11: A game reads input only through `PlayerInput` (`tilt()`, `pointer()`, `is_down()`, `button_pressed`, raw values).
  It must not use `scripts/net/`.
- REQ-GM-12: A game uses `App.server.haptic(slot, ms)` for feedback. It must not send network messages itself.
- REQ-GM-13: Game logic uses the frame `delta`. The result must not change with the frame rate.
  Fast physics use sub-steps of 1/120 s or less.

Players

- REQ-GM-20: The registry entry gives `min_players` and `max_players`. A game works with the number of players that are IN (REQ-GM-104) when it starts: the phones that are connected, except the ones that chose OUT.
- REQ-GM-21: A game must stay stable when a player leaves during play (the marker or object of that player is removed, no error). The base class calls `_on_player_left(slot)` once for each participant that left for good. The game removes the objects of that slot there.
- REQ-GM-22: A game must stay stable when all players leave (a lost phone first pauses the game, REQ-GM-30). It shows a menu with "Back to menu". The base class does this (`end_no_players()`), also when the game starts with no player. It sets `is_over`, and it does nothing when the game is over already.
- REQ-GM-23: The color of a player in the game is the slot color (`PlayerInput.color`). The names are the phone names.
- REQ-GM-24: All players use the same input mapping and the same sensitivity. No player has an advantage from the slot.
- REQ-GM-25: A game that needs a fair start gives all players the same start state (same distance to the goal).

Flow

- REQ-GM-30: While a participant is lost (the phone closed its connection, or nothing came from it for 3 s, for example no Wi-Fi or a phone call), the game is paused and a card says "2P LOST CONNECTION" (a player with a profile is named by the profile name: "MAYA LOST CONNECTION"), with a line for each lost player ("waiting to reconnect"). The base class does this. The game never goes on by itself, also not when the phone is back: the TV user chooses. The buttons are "Resume without 2P" (or the name of the player) (only while at least one other participant is connected), "Resume" (only when every participant is connected again; the title is then "2P reconnected") and "End game" (it ends the game at once, with no second question: the player chose it in a menu, issue #118; Back on the card still asks, REQ-GM-31a). The card changes by itself when a phone comes back or its slot is freed. The phones are in the phase `paused` while the card is open. The card for a phone that sends again changes within 10 s. When the lost phone is the only participant, the title of the card is "NO PLAYERS CONNECTED" (REQ-GM-22, issue #46) and the card lists it as waiting to reconnect; the buttons are the same, and the title changes to "1P reconnected" with Resume when the phone is back.
- REQ-GM-30a: The slot of a lost phone is kept 5 minutes while the game is paused for it (`Protocol.PAUSED_SLOT_GRACE_MS`, a phone call can be long), and 5 seconds in other phases (`Protocol.SLOT_GRACE_MS`, issue #44). When the time is over, the slot is freed and the participant leaves (REQ-GM-21). When every participant has left, the game shows "No players connected" with "Back to menu" (REQ-GM-22). When the only participant is lost, the card already says "No players connected" (issue #46) but waits for the phone. When every participant is lost, the card has no "Resume" (nobody is connected to resume with): it has only "End game" until a phone is back.
- REQ-GM-31: OK opens the pause menu: Resume, Try again, End game. (The button was called Restart until 2026-10-11, and End game was called Back to menu until 2026-10-21, issue #53.) **End game** (red with the focus) leaves for the Games screen at once, with no second question: the player chose it in the pause menu. Back closes the menu, and Back during play leaves the game after the question of REQ-GM-31a. Whether Back during play should also leave at once is an open question for the owner (issue #53); the question stays until the owner decides. **OK pauses with no hint (issue #228, analysis of 2026-10-30, Open):** a child who presses OK by accident sees the pause menu with **Resume** as the first item and the focus (`Minigame.open_menu` focuses the first item), so one more OK goes on; the pause is one press away from play, and the remote is the adult's (the phone is the controller, REQ-GM-37a). A "OK = PAUSE" hint for the first 5 s of a round would add a second line to a screen that has one hint line (REQ-GM-82), in every game, in two languages, over the world of the game (REQ-GM-49 keeps the HUD small). The rules of the project do not clearly favor it, so nothing is built until the owner decides: (a) leave as it is, or (b) a hint "OK = PAUSE" for the first 5 s of each round, or (c) the hint only in the first round after the app starts.
- REQ-GM-31a: Leaving a game that is in progress with Back asks first (End game in the pause menu does not, REQ-GM-31). Back opens "End the game?" with two menu items: "RESUME" (the default, the same word as in the pause menu) and "END GAME" (red with the focus). The game is paused while the question is open. Back on the question is "Keep playing". A game that is over (the result menu, "No players connected") leaves at once, without the question. The base class does this (`Minigame.request_leave()`). A game must not call `App.go_menu()` for a game in progress (only the End game item of the pause menu of the base class does), and it overrides `_in_progress()` when a game is in progress at a time the pause menu is not allowed. By default `_in_progress()` is `_can_open_menu()`. By default `_can_open_menu()` is true while `is_over` is false and a participant is left. A game sets `is_over = true` when it opens its result menu, and it overrides `_can_open_menu()` only to add limits.
- REQ-GM-32: Try again makes a new game with the same start values (`start_props`).
- REQ-GM-33: Every menu and every screen works with the D-pad, OK and Back. No touch or mouse is needed on the TV.
- REQ-GM-34: A game with a winner or a score ends on a result screen that shows the result and offers Try again and Back to menu. A game with scores uses `open_results()` (REQ-GM-72).
- REQ-GM-35: A game that shows a timer during play (a round clock, REQ-GM-71) starts with a visible countdown (3 s). Input does not move the players during it. `RoundClock` (`scripts/game/round_clock.gd`) keeps the countdown and the playing time. A game without a visible timer has no countdown: play (or the first turn) starts at once after Start in the settings view, its song starts with the play (REQ-GM-49a), and the game says so by returning false from `_has_countdown()` (decision of the owner, 2026-10-21: the countdown is only relevant where there is a timer). Timed games: Treasure Maze, Banana Party, Whack-a-Mole, Paint Grab, Car Race, Sheep Herding, Bumper Cars, and Tennis alone against the machine (the solo rally clock). Games without: Star Shield, Sumo Bumpers, Pin Pals, Mini Golf, Freeze Dance, Tower Builder (its turn time limits one drop and is not a round clock, decision 2026-10-30) and Tennis with 2 to 4 players.
- REQ-GM-36: A game must not open a menu that lets the player change the game setup during play.
  Setup choices (level, track, mode) are made before the game starts and on the result screen.
- REQ-GM-37: The pad of the phone has the Recenter box only in a game where the phone is a pointer at a target (Banana Party and Whack-a-Mole; the game says so in the `pad` list of its entry in the registry, issue #55). The box recenters (`PlayerInput.recenter()`) and is the only way to recenter during play: a game does not use A or B for it, so A and B are free for the actions of the game. In the other games the pad has no Recenter box, and the game recenters all players by itself at the start of play (or of a turn); the TV tells the phone with `rc: false` in `phase` and `welcome` (`docs/PROTOCOL.md`). Outside a game (menus, the debug overlay) the box is there.
- REQ-GM-37b: A tilt game recenters every phone at GO (the pose held in the countdown is neutral). When the phone is within 1.7 degrees of flat (screen up) at that moment, exactly flat is neutral, so a phone on a table gives no tilt (`Orientation.recenter(snap_flat)`, issue #124). The limit is small on purpose (3 degrees decided 2026-10-27, lowered to 1.7 degrees after the review of PR #133): a phone held still at 3 degrees would show a constant tilt of 0.05, above the dead zone of the maze (0.03, about 1.7 degrees). The value is a first guess that Test 9 decides. The Recenter box of the pad does not snap: the pose in the hand is neutral. Checked by `run_tests` ("recenter at 1.5 degrees from flat", "the Recenter button at 1.5 degrees", "recenter at 3 degrees").
- REQ-GM-37a: While a game runs, the pad of the phone shows only the controls that the game uses (issue #80). Each game lists them in the `pad` list of its registry entry: `a`, `b` and `recenter` (Pin Pals also has the aim strip on the turn of a phone, REQ-BW-4). A control that is not listed is not drawn, and a touch where it would be does nothing. The TV tells the phone with `ab` (the buttons: `a`, `b`, `ab` or empty) in `phase` and `welcome`, and with `rc` for Recenter (`docs/PROTOCOL.md`). A button that is alone stands in the middle of the row. A game with no control has an empty pad: the header, the score line and Disconnect stay. Outside a game (menus) the pad shows A, B and Recenter as before. The controls today: Banana Party and Whack-a-Mole A and Recenter; Sumo Bumpers, Pin Pals, Tennis and Mini Golf A; Treasure Maze, Car Race, Paint Grab, Sheep Herding, Bumper Cars and Star Shield none. A new game lists its controls (`add-minigame` skill).

Look and sound

- REQ-GM-40: Text and important shapes stay inside the 60 px safe margin of the 1920x1080 screen. This holds for every chip a game draws with `Shell.chip` or `Shell.score_chip` (the leader chip in the black top bar keeps the 60 px at the sides only), including the frame of the player on turn, and the hint plate (`Shell.hint`) of a game with chips at the bottom ends above them (issue #223). `tests/hud_layout.gd` checks every chip of every game against `Rect2(60, 60, 1800, 960)`, and that the hint does not cover a chip; `smoke_air_hockey` checks the hint during play.
- REQ-GM-41: Text on the TV is 32 px or larger (all text, also hints and chips). The rule is stated once, in REQ-FL-40 (`docs/TV_FLOW.md`; 28 px was an older value, issue #222). Text on the TV also has good contrast with the background (`UiTheme` colors).
- REQ-GM-42: A game uses `UiTheme` colors, the shell fonts, and mostly shapes made in code. Image, model and font files are allowed when `docs/TV_FLOW.md` (FD-9, FD-13) allows them. A game states its own asset files in its requirements file.
- REQ-GM-43: Important events give haptic feedback on the phone of the player: start (the end of the countdown, in a game that has one), hit, goal. The game file lists the scenes with a haptic (a "Sound and haptics" section). A player can turn haptics off on the phone (REQ-FL-66), so a haptic never carries information alone.
  Repeated events have a cool-down of 100 ms or more. Short pulses are 15 to 60 ms. A big event can be longer. `Haptics.pulse()` (`scripts/game/haptics.gd`) keeps the cool-down for each slot.
- REQ-GM-49a: A game makes sound only with `Sound.sfx(id)` of `scripts/audio/audio_manager.gd` (the effects are in `scripts/audio/songs.gd`). It does not make its own audio players. The song of the game has the id of the game and starts at "GO" (the base class does this); a game without a countdown (REQ-GM-35) starts its song with the play. The base class plays the countdown, pause and result sounds (REQ-FL-65).
- REQ-GM-49b: Every event with a haptic should also have a sound effect, and the game file lists them. No sound is scary or sad (REQ-GM-81): a miss, a fall and a loss are funny, soft or neutral. An effect is 0.5 s or shorter (a fanfare 2 s). A repeated event is quiet and has a gap (the manager drops the same effect inside 40 ms).
- REQ-GM-49c: The sound is for the TV only. The phone gets haptics (REQ-GM-43), and the game works the same with sound muted or haptics off.
- REQ-GM-49d: The name of the game on the HUD, in the settings view and on the Games screen is the key `registry.<id>` (never the English text). With the TV in Hebrew it shows in Hebrew (REQ-FL-87). A tile picture has no text, so it is the same in both languages. Test: `tests/game_names_hebrew.gd`.
- REQ-GM-44: The meaning of colors is the same in all games: accent = title or number, OK = good, BAD = danger.

Visual language (decision FD-14 in `docs/TV_FLOW.md`). Three tiers:

The 8-bit arcade style (FD-18) changed REQ-GM-45 and 46 (the shell) in phase 1. REQ-GM-47i to 47n (pixel worlds, a low-resolution game view) are new in phase 2 and apply to a game whose world is drawn in the pixel view (Sumo Bumpers first, Marble Race in phase 3; every 3D game is drawn in it). All five games are restyled (phases 2 to 4), so REQ-GM-47a, 47b, 47d (the neutral colors) and 47f are kept only for history and for a game that does not use the pixel view; a new game uses the pixel view. See `docs/ARCADE_STYLE_PLAN.md`.

- REQ-GM-45: Tier 1, the game shell (required). A game uses the shared shell for its pause menu, countdown (when it has one, REQ-GM-35), result screen, HUD text and score chips. It does not draw its own versions. The shell is part of `minigame.gd`, `minigame_3d.gd` and `shell.gd`, and it uses the arcade style (`UiTheme`, FD-18): the menus are text menus with a cursor in a double frame (REQ-FL-38, 41), the HUD text is 32 px, the countdown is 256 px and settles in 4 steps (REQ-FL-42), and all text is upper case. A hint at the bottom wraps to more lines when it is long.
- REQ-GM-45a: Tier 1, the black bar (required, owner, 2026-10-29, issue #123). Every pixel game has a black bar at the top, 112 units high (`Minigame.HUD_BAR_H`, the one constant: games and looks use it for their layout and draw no bar of their own) and as wide as the window on any window size, for the title, the timer and the chips. The shell draws it over the world (a game cannot leave it out or draw its world into it), so every game looks the same at the top. A game still draws its own world below it (the world may reach under the bar, as in Star Shield). A game without a pixel view (a 3D game) is not covered by this requirement. Checked by `pixel_render` (CI, 1080p and 4K) and `pixel_games`: the two edge columns of the bar are black in all games, in English and in Hebrew.
- REQ-GM-46: Tier 1. Everything that belongs to a player (marble, ball, cursor, score) uses the slot color from `Protocol`. A name or score chip is a black box with a 4 px `TEXT` frame, a square (24 px) in the slot color, the avatar of the player when there is one (REQ-GM-46b) and the text in `TEXT` (`Shell.chip`), because text on the slot colors has too little contrast in some pairs. The slot colors differ pairwise by a delta E (CIE76) of 25 or more, and each differs from an empty tile of the game by 40 or more (`auto_paint`, `auto_sumo`, `auto_asteroid` assert this). A player object (ball, marble, blob, bumper, cursor) shows **no number and no avatar**: players are told apart by the slot color alone; the name is on the chips. The countdown has no name tags: they were removed on 2026-10-21 (decision of the owner, Alon), because the players are told apart by the slot color (`tests/hud_layout.gd` checks that the countdown draws no name). A 2D ball is drawn with `Shell.ball()`. The HUD shows **one** chip, the leader chip (FD-21): the name and the score of the player in first place, or `TIE` with a gray square and the score when two or more players share first place. It is drawn by one function, `Shell.leader_chip()`, called by `Minigame.draw_leader_chip()`; a game returns its `Scoreboard` from `_scoreboard()` and gives no chip text of its own. The chip is as wide as its content (at least 200 px) and nothing in it is cut: a name of 12 characters (the longest the TV shows: 10 and a number, FD-22) and a score of 5 digits fit in one row, right of the title and the timer, and the chip ends at the right 60 px margin. A game with no score during play (the maze) returns no board and has no chip. The chip is also hidden while the best score is 0 (and in a race while no marble is ahead of the others), so a game starts without a chip and TIE never shows at 0 (`Scoreboard.has_lead()`). The HUD never needs a second row, so the play area is the screen inside the margin under one HUD row (about y 150). The score of each player is on that player's phone (REQ-FL-67), and all scores are in the result menu (REQ-GM-72). The meaning of accent, OK and BAD is the same in all games (REQ-GM-44).
- REQ-GM-46b: Tier 1. A chip with a player (the leader chip) shows the avatar of the profile next to the color square, 32 px (a 16 px picture at 2x, sharp pixels), before the name (`Shell.chip()`, `Shell.has_chip_avatar()`); a guest, a tie and an unknown avatar have no picture and the chip is as before. The chip grows by the picture and the name is never cut. A chip is drawn left to right in Hebrew too. Tests: `tests/game_helpers.gd`.
- REQ-GM-47: Tier 2, a toy-like world (required). A "key object" is a player object, a goal or a hazard. Values are for 1920x1080 and for the first version. The marble race trial (REQ-FL-47) checks them, and a change needs a change of this file in the same commit. The sub-requirements are 47a to 47h (toy-like worlds) and 47i to 47n (pixel worlds). In a pixel world, 47i to 47n replace 47a, 47b, 47d (the neutral colors) and 47f. A 3D world is a pixel world too: 47c (the outline hull), 47g and 47h stay, and 47j to 47l do not apply to meshes.
  - REQ-GM-47a: (Superseded by REQ-GM-47j: the outline of a key object is black, `UiTheme.OUTLINE`, one world pixel; the color `#1a0b45` is not used any more.) Old rule, kept for history: key objects have a dark outline in `#1a0b45` (`UiTheme.OUTLINE`).
  - REQ-GM-47b: (Superseded by REQ-GM-47j.) Outline width in 2D. 6 px for key objects of 40 px or more, 4 px for smaller ones. Use `draw_*` with the outline drawn first, under the fill.
  - REQ-GM-47c: Outline width in 3D. An inverted-hull mesh (a copy of the mesh, scaled out, front faces culled, unshaded, color `#1a0b45`) with a thickness of 8% of the smallest size of the object, limited to 0.03 m to 0.10 m. A game does not use a shader for it.
  - REQ-GM-47d: Color of key objects. Flat color, no gradient, no texture. HSV saturation 0.55 or more and value 0.60 or more. Player objects use the slot color from `Protocol`. A neutral object (for example a post) uses a Party Pop accent (cyan `#3ddcff`, yellow, pink) with the outline. A pale grey is not allowed: it looks unlit and out-shines the player objects.
  - REQ-GM-47e: Contrast. A key object is at least 48 px high on the screen in the normal view (the camera at its lowest height, for a 3D game). A key object and its background differ in luminance by a ratio of 3:1 or more. The ground and the background have saturation 0.35 or more and value 0.25 to 0.65, so the key objects are the brightest things on the screen. (The marble race trial found that the Party Pop purple has saturation 0.84, so the upper saturation limit was removed.)
  - REQ-GM-47f: (Superseded by REQ-GM-47l and REQ-FL-38: no round corners in the arcade style; shapes are stepped by the pixel grid.) Rounding in 2D. Key objects have a corner radius of 25% of their shorter side or more (a circle or a capsule is fine). Maze walls and other long shapes have round ends.
  - REQ-GM-47g: (Superseded by REQ-GM-47l; no registered game is drawn in 3D.) Rounding in 3D. Key objects are spheres, capsules, cylinders or meshes with a bevel of 15% of the shortest side or more. A sharp `BoxMesh` is allowed only for large flat world parts (floor, wall, platform).
  - REQ-GM-47h: Materials and light in 3D. `StandardMaterial3D` with `metallic` 0, `roughness` 1, no texture, no emission except for a goal (up to 0.3). One directional light, and an ambient light so that the shaded side of a key object is not darker than 60% of its lit side. The pattern of a finish line or a checker is made with geometry or vertex colors, not with a texture file.
  - REQ-GM-47i: Pixel view. A 2D game may draw its world into a low-resolution view of 480x270 (`Minigame.PIXEL_VIEW`) that stands for the whole screen. The game returns true from `_pixel_world()` and draws the world in `_world_draw()` in screen units (1920x1080 at the TV). The view is scaled up with nearest filtering to the screen, so one world pixel is 4x4 screen pixels at 1080p and 8x8 at 4K. It has no antialiasing and no shader. The shell (HUD, chips, timer, countdown, hints, menus, the dim layer) is drawn at full resolution above the view and never goes through it. The view follows the size of the game node. A 3D game (`minigame_3d.gd`) renders its camera into a view that is 270 rows high and as wide as the game node needs to keep the pixels square (480x270 on a 16:9 screen; `Minigame3D.view_size_for()`), with no antialiasing, and `world_to_hud()` gives the full-resolution HUD position of a point of the world.
  - REQ-GM-47j: Pixel outline. A key object in a pixel world has a black outline (`UiTheme.OUTLINE`) of exactly one world pixel (`Shell.WORLD_PIXEL`, 4 units), drawn first under the fill (`Shell.pixel_ball()` for a ball).
  - REQ-GM-47k: Pixel colors. Flat colors, no gradient, no texture, from a limited world palette that the requirements file of the game lists (at most 8 colors, and the arcade colors of `UiTheme` count). A few more colors are allowed when the look of the game needs them (for example a light show), as long as the general theme is kept: flat colors, no gradient, and the palette still reads as the same arcade world. The requirements file of the game lists the extra colors and why. Player objects use the slot colors from `Protocol`.
  - REQ-GM-47l: Pixel shapes. Shapes are stepped by the pixel grid; there is no rounding rule. A position is moved to the grid with `Shell.snap()` before it is drawn, so that a shape does not shimmer between two pixels. A scale change (a fall, a pop) goes in steps of a quarter.
  - REQ-GM-47m: Pixel size and contrast. A key object is 12 world pixels (48 screen pixels at 1080p) or more high, and a key object and its background differ in luminance by 3:1 or more (as REQ-GM-47e).
  - REQ-GM-47n: Pixel text. No text is drawn in the pixel view. A word in the world ("Whee!") is drawn by the HUD at the position of its object. An object has no number (REQ-GM-46).
  - REQ-GM-47o: Languages (FD-19, REQ-FL-54, 63). Every text the shell draws goes through `Lang` (`Shell.title`, `text`, `hint`, `countdown`, the menus and the result list), and a game builds a text with a name or a number with `Lang.f()` from a format string, never by joining pieces. In Hebrew (right to left) the HUD is mirrored by the shell: the title is at the top right, the leader chip is at the left margin, the timer box is at the right. The timer box has **one place in every game** that has one (`Shell.TIMER_X`, `Shell.TIMER_Y`): its left edge is at x 520 and its top at y 36 on a 1920 wide screen in English, and its right edge is at x 1400 (1920 - 520) in Hebrew (`Shell.mx`). Car Race has no place of its own (it was at x 640). The title is left of it and the leader chip is right of it, so they never overlap, a chip is laid out left to right in both languages (the color square, the avatar, the name, the score) and a game puts its own HUD text with `Shell.mx()`. Audience: children too

- REQ-GM-80: Games are for children as well as adults (from about 5 years), played together on a sofa. A game is checked against REQ-GM-81 to 84 when it is made and in its device test.
- REQ-GM-81: Content is friendly. No violence against people, animals or any living or made-up creature, no blood, injury or death, no scary pictures or sounds. A game can be playful: throw snowballs, bump, race, roll, or shoot toy beams at lifeless things (rocks, balloons, targets). Nothing alive is shot. A beam, a ball or a bump is a bright toy and makes a soft sound. The characters are made up, kind and funny. When something is "hit", it reacts in a funny, harmless way (it is covered with snow, it spins, it floats away, it bursts into colored pixels). Nobody cries or falls down hurt.
- REQ-GM-82: A child understands the game from one hint line and a few seconds of play. A player needs the pointer or the tilt and at most one button (A). Targets and objects are large. The pace is slow at the start. The text on the screen is short and plain.
- REQ-GM-83: Mistakes are cheap. A miss, a fall or a bump takes no points away. A player can be out of a round (a hit, last one standing) when the game is built on it. Then the player keeps the points, can watch the game, and the wait is short (about 20 seconds at most), or the player comes back (the next round, or after a few seconds), or the game is a team game that ends when the last player is out, so the wait lasts only as long as the others play. The game file says which of these applies.
- REQ-GM-84: Words are kind. Titles and messages are positive ("Nice throw!", "Splat!", "X wins!"). No text says "You lose", "Game over" or "Failed". A ranking shows the winner and the others without mockery.
